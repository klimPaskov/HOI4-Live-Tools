# Porting status: macOS, Linux and Windows

The native runtime (`native/`, Rust) is developed and played on macOS. This page says, per
platform, which of its tools exist, compile, have a memory layout for the current game version
and were last proven against the running game, and what is left to finish each port. It is kept
current by hand; the check in `tests/test_xlayout_coverage.py` keeps the Linux layout list honest.

Game version: HOI4 1.19.4.1 on macOS (1.20.0.0 through the generated variant below), 1.20.1.0 on Linux.
A newer build needs its own layout table, made with
`scripts/game_migrate.py` ([Game versions](GAME_VERSIONS.md) has the steps, the measured accuracy and
what a user gets on an unsupported build). Every port must be on the same game version as the macOS
keys' build or have its own table for its build. The keys stay the macOS 1.19.4.1 values for good: macOS
1.20.0.0 runs on a runtime generated from the migration map (`scripts/macos_build_variant.py`), so the
macOS sources do not move and Linux and Windows tables are never re-keyed; a 1.20 table for Linux or
Windows is keyed by the same 1.19.4.1 values. The old-to-new map stays committed for reference
(`native/layouts/migrations/macos-DFA875A5-to-ED135FE5.json`; `scripts/game_migrate.py rekey` applies it to
a table keyed otherwise). The tool catalogue has 189 `hoi4_*` names (about
181 player tools plus debug tools; `hoi4-live-native --list-tools` prints them).

## Linux

The tools in `native/src/launch/macos/` are compiled for Linux too and are served by the owned
Linux launcher (`--serve`, then `--bind-management` with an X11 window). Every memory address and
field offset a tool reads goes through `xlayout`: macOS values are the keys, and the Linux build
looks them up in `native/layouts/linux-<build id>.json`. A key missing from the table fails that
read with `layout_unmapped`; nothing is guessed.

What works:
- The 150 tools that existed on 5 November 2026 were run against the Linux game on that date
  ([record](LIVE_VERIFICATION_LINUX_1_19_4.md)).
- The executor (`hoi4_autopilot`) and the change watcher (`hoi4_observe`, `hoi4_wait_change`) run in
  the Linux supervisor once the management tools are bound, as they do beside the macOS server.
- The learning tools (`hoi4_ui_inspect`, `hoi4_ui_act`, skills and facts) scan the Linux window
  roots (+0x338 views, +0x330 pop-ups) measured on the Linux game.

What is missing:
- 39 tools were added after the Linux live check (battles, army orders such as gather, detach, attack and
  fallback, occupation and its laws, stockpile, war statistics, operations, railways, the learning
  tools, the executor and watcher). None has run on Linux.
- 1 image key and 62 field keys the tools use are not in the Linux 1.20.1.0 table. They are
  listed by source file in `scripts/data/xlayout-unmapped-1.20.1.0.json`; the tools that need them
  refuse on Linux until they are mapped.
- No screen recorder (the macOS recorder uses ScreenCaptureKit).

The Linux build is 1.20.1.0 (GNU build ID `8e7ff8b3de4402d28ada7f7c976e7464e1fbe458`, SHA-256
`0ad0c8cad5c8f65d86750454afd79c3f26ba5ca9e0f205a3abfaa8dff96c57a9`). Its table joins two results.
One is generated by `scripts/game_migrate.py` against the macOS key build (report
`native/layouts/linux-8e7ff8b3....coverage.json`). The other moves the 1.20.0.0 table (build ID
`71806afa`) with `scripts/linux_build_migrate.py OLD NEW --table`: all 214 image values mapped, every one
at its 1.20.0.0 address (only `.rodata` grew, by 16 bytes), and 3,368 of 3,420 fields (report
`native/layouts/migrations/linux-71806afa-to-8e7ff8b3.json`). The two agree on all 212 image keys and on
3,245 of the 3,251 fields they share. Where they differ the table keeps the moved value: it is the
1.20.0.0 value, four of the six were confirmed on the running 1.20.0.0 game, and the generator reached the
others through other classes' functions. Entries only the move found are marked `migrated` in the
table's `confidence` section.

The 1.20.0.0 table came the same two ways from the 1.19.4.1 one (`linux_build_migrate.py --table`,
report `native/layouts/migrations/linux-2265e6e7-to-71806afa.json`, and `game_migrate.py`); the core
modules' own Linux values moved with the literal mode then and kept their addresses in 1.20.1.0.

Live check on 24 November 2026 (owned 1.20.0.0 game on Xvfb, GER 1936, management tools bound):
32 read tools were called. 46 fields the move had left out were confirmed: carried unchanged from
1.19.4.1, each made a tool that refused without it return the right GER values
(`scripts/data/xlayout-live-1.20.0.0.json` names the tool and the values). With them, 23 of the 32
tools read; `hoi4_stockpile`, `hoi4_commanders`, `hoi4_armies`, `hoi4_wars`, `hoi4_events`,
`hoi4_occupation`, `hoi4_war_stats`, `hoi4_convoys` and `hoi4_battles` refuse on keys that were
already unmapped on 1.19.4.1.

Steps to finish, in order:
1. Live reads for the remaining keys, added as live entries with their evidence.
2. Run the new tools against the Linux game (any x86_64 Linux with an X server; a virtual display
   such as Xvfb with software rendering works but is slow in war) and add what differs to
   the live entries with its evidence.
3. A recorder for X11 (for example ffmpeg `x11grab` on the owned display) if Linux campaigns are to
   be filmed.

Without the executable, `python3 scripts/gen_linux_layout.py extend native/layouts/linux-<id>.json`
fills the keys whose class has mapped neighbours with the same shift (the generator's bracketed
rule) and prints the rest by source file; `--write` stores the fills, `--unmapped FILE` the list.

## Windows

Two runtimes exist:
- The Python runtime (`hoi4_live/`, 52 tools) reads the screen with Windows OCR and drives the game
  with ordinary input. It is the supported Windows path for mod testing and was last run on
  Windows HOI4 1.19.4.2. It has no memory reads and is not a campaign runtime.
- The native runtime has a read-only Windows process reader (`native/src/platform/windows/`) with
  an empty build allowlist, a `Process` for a game it started itself (`WindowsProcess`: the game's
  parent must be the running server, identities by creation time, SID and file ID) and a launcher
  (`hoi4-live-native --windows-serve CONFIG`) that starts `hoi4.exe` without Steam variables in a
  private user folder, refuses while a game or the Steam client runs, and restores the launcher
  settings it redirected when the game exits (`--windows-restore RUN` repairs an interrupted run).
  Windows strings are MSVC `std::string`/`std::wstring`; `object_type` reads the MSVC complete
  object locator. The core game and army layouts for Windows 1.20.0.0 were read live from an owned
  game (globals, date, speed, pause, player tag, countries, difficulty, playthrough, the country's
  member objects, division strength and organisation, the tag database; checked through the tools on 24
  November 2026: `hoi4_overview` and `hoi4_army` on a paused game). The division province and the
  production members are not measured yet and fail with `read_bound`. Every read batch runs the full
  ownership census (tens of milliseconds), so a multi-read snapshot of a running game tears
  (`torn_read`); reads of a paused game work. It sends no input: a
  development build (`--features dev-table`) reads a table from `HOI4_LIVE_DEV_TABLE` and accepts
  the executable named by `HOI4_LIVE_DEV_WINDOWS_SHA256`; release builds attach to nothing.
  The management tools are compiled and unit-tested on Windows, but nothing binds them there yet.
  Their journals hold the exclusive lock on a sibling `<journal>.lock` file on Windows (a Windows
  lock on the journal itself would stop every other reader); the daily plan store still refuses on
  Windows (its owner-only atomic writes are not verified there).

Steps to finish, in order:
1. Done: the tool modules compile on Windows and Windows CI runs their unit tests.
2. The private-file checks (controller state, daily plan store) for Windows: owner-only ACLs
   instead of POSIX modes.
3. Done (not yet run against the game): a `Process` for an owned Windows game and a launcher that
   starts it without Steam variables in a private user folder, like the Linux launcher.
4. A `GameInput` for Windows (`SendInput` to the owned, foreground window; client geometry, DPI,
   keyboard layout), with the modifier timing the Linux backend needed.
5. A layout table for the Windows build. Started: `scripts/pe_rtti_map.py MACHO PE` maps every
   vtable key the sources use (the `Class` tags, the `img()` vtables and the `*vtable*` values of
   the hand-written core layouts) to the PE by RTTI name: the Itanium typeinfo name of the macOS
   address point is rewritten in MSVC form and looked up through the complete object locators.
   Windows 1.20.0.0 (`hoi4.exe` SHA-256 `1beb2a38fe2d...d2ac1b63a9f`, the current Steam build) and
   1.19.5.0 (`709f916afbeb...01fce148`) give the same result: 177 keys with high confidence
   (primary vtable), 4 with medium (secondary vtables matched by order), one template left
   (`TNullObject<CBuildingTemplate>`) and 8 globals the mapper cannot map
   (`scripts/data/windows-<version>-vtables.json`, report beside each). RTTI names do not change
   between versions, so the vtables hold even though the keys come from macOS 1.19.4.1; a class
   whose fields changed still needs its fields checked live. The mapper
   (`scripts/cross_platform_map.py`) reads Mach-O and ELF only; `scripts/game_migrate.py identify`
   reads a PE's build id (CodeView GUID and age). For a PE executable it can be
   extended for vtables (MSVC RTTI names translate from Itanium names) and for globals reached
   through matched functions, but MSVC code differs from clang code far more than gcc code does,
   so field offsets will mostly come from live reads: MSVC `std::string` is 32 bytes like
   libstdc++ but `std::map`, `std::list` and hash containers have other sizes and layouts.
6. Live checks of every tool on a Windows game, recorded like the Linux record.

## Continuous integration

| Workflow | macOS | Linux | Windows |
|---|---|---|---|
| Native Rust | fmt, clippy `-D warnings`, `cargo test` | the same, plus aarch64 clippy, the Yama-gated reader test and an Xvfb input fixture | the same full set (nine tests ignored there with the reason: the daily plan store and three that read a locked journal), plus the owned reader fixture |
| Python | unit tests on 3.9 and 3.13, plan-key check, protocol smoke | the same | the same |

`tests/test_xlayout_coverage.py` (Python workflow, every platform) fails when the sources use a
layout key that is neither in the Linux table nor listed as unmapped, and when a listed key has
been mapped, so each new macOS tool shows its Linux cost in its own pull request.

Known flaky on Windows runners: the focus and research stage timing tests. If only those fail and
the change does not touch them, rerun the failed job once before investigating.

No GitHub-hosted runner can run the game; live checks need a machine with the game installed.
